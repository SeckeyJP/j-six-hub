# ADR-0003: 案件を複数にし、実データ2件と架空の案件1件を1本の時間軸で再生する

## ステータス

承認

## 日付

2026-09-22

## コンテキスト（背景）

案件が1件（approval-workflow）だけでは、Hub が複数の案件を横断して管理するものだということが伝わらない。
一方で J-SIX Hub の要点のうち、**複数ベンダーの間の Interface Contract** と **ローカル退避**は、J-SIX の実行記録に存在しない。

J-SIX にはもう1つ実行記録のあるサンプルがある。

- `examples/monthly-billing`（月次請求書発行）
  - 2026-09-18〜19 の初版：PR #4。Spec・hold-out・TDD 実装・G3 の指摘への対応・工程成果物を、時刻付きのコミットで記録
  - 2026-09-21 の TASK-MB-007（振込先口座の印字）：PR #18
    - タスク定義（`docs/tasks/TASK-MB-007.md`）と、hold-out・Red・Green のコミットがある
    - G3 の指摘を受けた修正が5回あり、CI で整形漏れが見つかった
    - `reports/gate-history.jsonl` に、G1 スコープ検査による停止（AI が許可範囲外の hold-out テストを変更）と、G3 の再判定要求が時刻付きで残っている

## 判断（Decision）

1. **案件ごとにデータを分ける**。`data/projects.json` に Program と案件の一覧を置き、イベントは `data/projects/<案件ID>/events.jsonl` に置く。抽出の対象と再構成イベントも案件ごとに置く
2. **案件は3件**にする
   - approval-workflow（実データ）
   - monthly-billing（実データ）：Git のコミットと `gate-history.jsonl` から抽出する。セッション記録は使わない
   - 受発注連携（**架空**）：複数ベンダー・Interface Contract 違反・エスカレーション・ローカル退避を見せる。全イベントを `reconstructed` とし、根拠に「架空のシナリオ」と書く
3. **架空の案件は `projects.json` で `fictional: true` とし、画面で常に「架空」と表示する**（決定事項 D5）
4. 3件を束ねる Program（「社内業務システム刷新（説明用）」）も説明のための架空のまとまりとし、画面にその旨を表示する
5. **再生は全案件で1本の時間軸**にする。全案件のイベントを時刻順に並べ、再生位置 n までに含まれるイベントで各案件の状態を計算する。こうすると、複数の案件が並行して進む様子を1つのスライダーで見せられる

## 理由（Rationale）

- 2件目を実データにすれば、複数案件の画面でも実測の比率を保てる
- ベンダー間の契約やローカル退避は実データに無い。架空の案件1件にまとめて明示すれば、実データの案件と混ざらない
- 案件ごとの状態の計算は、これまでの `replay` をそのまま使える

## 検討した代替案

| 代替案 | 却下理由 |
|---|---|
| 実データ1件に架空の案件を複数足す | 実測の比率が下がる。実データで2件目を用意できる |
| 実データ2件だけ | 複数ベンダーと Interface Contract を見せられない |
| 案件ごとに別々の時間軸で再生する | 複数の案件を同時に管理している様子が伝わりにくい |

## 影響（Consequences）

### ポジティブな影響

- 案件一覧で、進み具合と注意点（順序違反・ゲートでの停止・契約違反）を案件ごとに並べて見せられる

### ネガティブな影響（トレードオフ）

- 実データの2件は日付が離れている（2026-06 と 2026-09）。1本の時間軸では、先に approval-workflow の初版だけが進む
- 架空の案件のイベントは、時刻も含めて著者が組み立てたものである

### 将来の注意事項

- 架空の案件を実データの案件と同じ集計（実測の比率など）に混ぜない。混ぜる場合は、架空であることを併記する
