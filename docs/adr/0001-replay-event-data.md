# ADR-0001: リプレイ用イベントを実行記録から抽出し、実測と再構成を分けて1本の JSONL にする

## ステータス

承認

## 日付

2026-09-22

## コンテキスト（背景）

リプレイ型サンプル（J-SIX `docs/control-plane/adr/0004-replay-sample-environment.md`）は、
J-SIX の実行記録を Hub の画面上で再生する。題材は J-SIX の `examples/approval-workflow` で、記録は次のとおり残っている
（2026-09-22 に調査）。

| 記録 | 公開 | 内容 |
|---|---|---|
| Git のコミット | 公開 | 2026-06-15 の初版（squash 1件）、2026-09-19 の PR #5（Skill 実行と TASK-AW-002 の hold-out / Red / Green / Refactor を時刻付きで15件） |
| Claude Code のセッション記録 | **非公開**（著者の手元） | 2026-09-19 の Skill 7本の実行。サブエージェント（hold-out・Red・Green・Refactor・scope-judge）の開始・終了、Stop hook のブロックとゲート判定の出力 |
| ゲート結果・証跡パッケージ | 元ファイルの公開は未確認（2026-09-23 訂正。ADR-0005） | `reports/`（証跡パッケージ、G3 判定、CI でのゲート失敗の履歴） |

一方、次のものは記録が存在しない。

- 人間の承認（Spec・証跡パッケージの承認欄は空欄のまま）
- Hub 固有の出来事（タスク投入、プロセス定義・憲法の版の固定）。当時 Hub は存在しなかった

## 判断（Decision）

1. **イベントは1本の JSONL**（`data/events.jsonl`）にし、1行1イベントとする。形式は `data/events.schema.json` で定義する
2. **全イベントに `provenance` を付ける**
   - `measured`：記録（Git・セッション記録・レポート）から抽出した出来事
   - `reconstructed`：記録が無いため著者が組み立てた出来事。**組み立てた根拠を `basis` に必ず書く**
3. **状態はイベントに持たせない**。Phase・タスクの状態は、画面がイベント列と J-SIX のプロセス定義（`process-v0.1.0`）から計算する。状態遷移そのものを記録すると、Hub が存在しない当時の出来事がすべて再構成になり、実測との区別がぼやけるため
4. **抽出はスクリプトで行う**（`tools/extract_events.py`）。セッション記録は著者の手元にしかないため、抽出は手元で実行し、生成した `events.jsonl` をコミットする
5. **セッション記録から持ち出すのは次のものだけ**とする
   - 時刻、Skill 名、サブエージェントの種類、ツール呼び出しの件数
   - Stop hook によるゲート判定の各行（`✅ [G2] tests: 全 45件 通過` の形）。ローカルの絶対パスは除去する
   - プロンプト・応答・ツールの入出力の本文は持ち出さない。prompt 型 Hook のブロックは件数だけを記録する
6. **再構成イベントは手書きのファイル**（`data/reconstructed.json`）に置き、抽出スクリプトが実測イベントと時刻順に合流させる
7. 抽出スクリプトは **Python 3.9 以上の標準ライブラリだけ**で書く。J-SIX の Plugin のスクリプトと同じ方針で、手元の実行に追加のパッケージを要らないようにする。Web アプリの技術スタックとは独立に決める（Web アプリは H4 の冒頭で別の ADR にする）

## 理由（Rationale）

- 実測と再構成を同じ形式に並べ、ラベルで区別すれば、画面は1つの読み込み処理で両方を扱える。区別は画面に常時表示できる
- `basis` を必須にすることで、再構成がどの記録のどの欠落を補ったものかを読者が追える
- 状態を画面側で計算すれば、プロセス定義の版を上げたときにイベントを作り直さずに済む

## 検討した代替案

| 代替案 | メリット | デメリット | 却下理由 |
|---|---|---|---|
| Plugin にイベント出力 Hook を追加して再実行する | 記録の形式を揃えられる | Plugin の版上げと評価の再実行が必要。再実行しても人間の承認は記録されない | 既存の記録で主要な出来事を実測できるため、今は不要 |
| セッション記録を丸ごと公開する | 最も詳しい | プロンプト・出力の本文やローカルのパスを含む | 公開物に持ち出す情報を最小にする |
| 状態遷移もイベントとして記録する | 画面の実装が単純 | 当時 Hub が無かったため、ほぼ全件が再構成になる | 実測の比率が下がり、区別の意味が薄れる |
| 手作業で events.jsonl を書く | 道具が要らない | 再現できず、誤りを検証できない | 実測部分は抽出を再現可能にする |

## 影響（Consequences）

### ポジティブな影響

- 実測イベントはスクリプトで再生成でき、手作業の転記ミスが入らない
- 人間の承認が記録されていないこと自体が、再構成ラベルとして画面に現れる

### ネガティブな影響（トレードオフ）

- セッション記録は著者の手元にしかないため、第三者は抽出を再現できない。Git とレポート由来のイベントは再現できる
- 2026-06 の初版は squash 1件で、Phase ごとの時刻が無い。同じ時刻に並ぶイベントの Phase 内の順序は再構成になる

### 将来の注意事項

- 再構成イベントを追加するときは `basis` に根拠を書き、実測イベントと矛盾しないことを確認する
- セッション記録から持ち出す項目を増やすときは、本 ADR を改訂する
