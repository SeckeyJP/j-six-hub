# Design Spec — J-SIX Hub リプレイ型サンプル

**版**: 1.2 | **日付**: 2026-09-23 | **Phase**: P2（1.2 で §6.10 を追加） | 要求: [requirement-spec.md](requirement-spec.md)

---

## 1. アーキテクチャ

```
[ビルド時]
  scripts/fetch-process.mjs ── J-SIX process-v0.1.0 の yaml を取得
        │                      process.lock.json の SHA-256 と照合 → .cache/process.json
        ▼
[ブラウザ]
  data/events.jsonl ─┐
  process.json ──────┤
                     ▼
  src/replay/  （React に依存しない。純粋関数）
     replay(events, process, n) → HubState
                     ▼
  src/ui/    （HubState を表示するだけ）
     レイアウト・再生操作・各画面
```

技術スタックは [ADR-0002](../adr/0002-web-app-stack.md)。

## 2. データ

### 2.1 入力

- **イベント**：`data/events.jsonl`（[ADR-0001](../adr/0001-replay-event-data.md)、`data/events.schema.json`）
- **プロセス定義**：J-SIX `process/jsix-process.yaml`（`process-v0.1.0`）。使うのは `phases`・`gates`（層・チェック・承認者の役割）・`roles`・`check_kinds`・`deviations`・`state_machines`

### 2.2 取り込みの手順（プロセス定義）

1. `process.lock.json` の `tag` と `path` から URL（raw.githubusercontent.com）を組み立てて取得する
2. 取得した内容の SHA-256 が `sha256` と一致しなければ失敗する（改変・取り違えの検出）
3. YAML を JSON に変換して `.cache/process.json` に置く（コミットしない）。キャッシュがありハッシュが一致すれば取得しない

## 3. リプレイの計算（`src/replay/`）

### 3.1 HubState

| 項目 | 内容 |
|---|---|
| `n` | 適用したイベント数 |
| `current` | n 件目のイベント（無ければ null） |
| `iteration` | 直近のイベントの一周の名前 |
| `project` | 登録された案件、固定したプロセス定義の版、憲法の版 |
| `phases[]` | プロセス定義の順に、Phase の ID・名前・ゲート・状態（`not_started` / `in_progress` / `approved`）・逆戻りで開き直したか |
| `tasks[]` | タスクの ID（無ければ「ID なし」）・状態・現在の工程・サブエージェントの履歴・ゲート記録の有無 |
| `evaluations[]` | ゲートの判定（`gate.evaluated`）。起動元・結果・回数・層ごとの結果 |
| `approvals[]` | 承認（`gate.approved`）。有効か・無効ならその理由 |
| `deviations[]` | 逸脱。種類・開始／終了イベント・タスク・周・開始時の投入 seq |
| `violations[]` | 順序違反。違反したイベントと、承認されていなかった Phase |
| `requirements` | その時点の要件（REQ）と性質（PROP）、直前の更新で追加された ID |
| `traceability` | 要件 ⇔ テスト ⇔ 実装（⇔ ADR）の対応と、テストが対応していない要件 |
| `counts` | 実測・再構成の件数 |

### 3.2 規則

`replay` は空の状態から先頭 n 件を順に適用する（REQ-004）。各イベントの扱いは次のとおり。

| イベント | 状態への反映 |
|---|---|
| `project.registered` | 案件を登録する。P0（`mode: continuous`）を進行中にする |
| `process.pinned` / `constitution.pinned` | 版を記録する |
| 作業のイベント（`commit.created`・`ai.*`・`gate.evaluated`・`hook.blocked`・`task.dispatched`）で `phase` があるもの | その Phase が未着手なら進行中にする。承認済みならそのまま。**P1 以降で、それより前の Phase（P0 を除く）に承認済みでないものがあれば順序違反を記録する**（REQ-011） |
| `gate.approved` | ゲートの Phase を求める。**有効な承認**（実行者が人間で、役割が記録されていればゲートの承認者の役割に含まれる）なら Phase を承認済みにする。人間でなければ無効（理由「承認者は人間の役割に限られる」）、役割が承認者に含まれなければ無効（REQ-009） |
| `deviation.opened` | 逸脱を開く。`phase_rollback` なら `to_phase` を作業中に戻し、既承認の `to_phase` 以降には以前の承認を履歴として残したまま「再承認待ち」を付ける。未承認の後続工程は開始しない（REQ-010） |
| `deviation.closed` | `payload.opened_by` で開始を特定し、種類・task・iteration が一致する未終了の逸脱だけ閉じる。旧データは同じ種類・タスク・周・実行の候補が一意の場合だけ適用する（ADR-0004） |
| `task.dispatched` | タスクを待機で作る。ID が無いタスクは「一周名 / ID なし」で識別する |
| `ai.session.started`（task あり） | タスクを実行中にする |
| `ai.agent.started`（task あり） | 現在の工程を `payload.step` にする。G3 なら判定中にする |
| `commit.created`（task あり） | 工程を記録する。task が無く P4 のコミットなら、同じ一周の ID なしタスクを「合格（ゲート記録なし）」にする |
| `gate.evaluated` | 判定を記録する。task の投入が一意に特定できた場合だけ、`passed` で合格、それ以外で不合格にする。再投入後の判定は `payload.dispatch_seq` で対象の `task.dispatched.seq` を指定する（ADR-0006） |
| `requirements.updated` / `traceability.updated` | その時点の一覧で置き換える。要求にあってテストが無い要件を「テスト未対応」として数える |

**per_task の Phase（P4）**は、タスクが1件以上あり全タスクが合格したとき承認済みとみなす（プロセス定義の遷移 `all_tasks_done`）。承認済み後にタスクを再実行・追加したときは、そのタスクを含めて再評価が終わるまで進行中とする。
逆戻りで開き直した後は、**開き直した後に投入したタスク**だけで判定する（前の周に合格したタスクで完了にしない）。
同じ task・iteration の再投入が複数あり `dispatch_seq` のない判定は、到着順から対象を推測せず、監査履歴に残してタスク完了には使用しない。

### 3.3 Property の実装方針

| PROP | 方針 |
|---|---|
| PROP-001・002 | 実データと、実データから作った乱数のイベント列で、任意の n と操作列について検証する（PBT。ライブラリは fast-check） |
| PROP-003 | 任意の n について、承認済みの非 per_task Phase に有効な承認があるかを検証する |
| PROP-004 | 任意の n について `counts.measured + counts.reconstructed === n` |

## 6. 複数案件と説明（v1.1）

### 6.1 時間軸

全案件のイベントを（時刻, 案件の並び順, seq）で1列に並べる。再生位置 n までに含まれる各案件のイベント数で、
案件ごとに `replay` を呼ぶ（`replayProgram`）。

### 6.2 タスクの状態の追加

| イベント | 反映 |
|---|---|
| `task.dispatched` の `payload.team` | タスクの担当（チーム・ベンダー）にする |
| `deviation.opened`（task あり） | `escalation`・`interface_contract_violation` なら「エスカレーション中」、`local_fallback` なら「ローカル退避中」 |
| `deviation.closed`（task あり） | 対応する開始が見つかったときだけ、開始時のタスク実行の残る逸脱から状態を再計算する。退避が残れば退避中、それ以外の停止例外が残れば判断待ち、残らなければ実行中 |
| `commit.created`（task なし・P4） | ID の無いタスクを合格（ゲート記録なし）にするのは、**コードを含むコミット**に限る |

### 6.3 統制記録・停止位置と説明文

- **統制記録**：あるイベントを適用したとき、ゲートの判定が停止・未達、無効な承認、逸脱の開始、順序違反の発生のいずれかが起きたもの
- **停止位置**：統制記録のうち、ゲートの判定が停止・未達、または Hook が停止したもの。再生バーの赤い印と「次の停止へ」はこの位置だけを使う
- **説明文**（`narrate`）：イベントの種類ごとに「いま起きたこと」（見出しと補足）と、再生モデル上の解釈・構想で想定する動作（統制記録のとき）を返す。
  文はイベントとプロセス定義から組み立て、画面のコードに Phase やゲートの一覧を書かない

イベントの provenance と説明の由来を分離する。実測の停止・未達は「元記録」、再構成イベントの見出しは「再構成」、将来の動作は「構想」とする。順序判定には承認時刻の再構成による限界を添える。主体の `system` は「システム」とし、Hub の実行実績とみなさない。

### 6.4 画面構成

| 領域 | 内容 |
|---|---|
| 上部 | タイトル、リプレイの表示、ガイドを開くボタン |
| 左 | Program（架空の表示）、案件の一覧（状態と注意点）、選んだ案件の画面切り替え |
| 中央 | いま起きたこと、選んだ画面 |
| 右 | 出来事の記録（凡例・絞り込み・統制記録の強調） |
| 下部 | 再生操作（停止位置をスライダー上に印で示す） |

ルートは `#/`（案件一覧）と `#/p/<案件ID>/<画面>`。いずれも `?n=<再生位置>` を付けられる（REQ-026）。
再生位置を動かすと `history.replaceState` で URL を書き換える（履歴を汚さない）。

### 6.5 工程ボードの印と、履歴への導線

工程のカードには、その工程で働いた統制を印で出す（REQ-010）。印が無いときも場所を確保する（REQ-022）。

| 印 | 出す条件 |
|---|---|
| ● いまここ | 作業中の工程。無ければ、まだ始まっていない工程を除いた最後の工程 |
| ⚑ 検査で停止 n | その工程の検査で `blocked` / `failed` になった回数 |
| ⚠ 順序違反 n | その工程が、前の工程の承認前に始まった回数 |
| ↩ 再承認待ち | Phase 逆戻り後、以前の承認を使わずに承認を取り直す工程 |

印の欄の高さは、印が最も多い場合（1つのカードに4つ）に必要な高さをブラウザで測って決める。

順序違反に出る出来事 ID は履歴の該当行を開く。絞り込みで隠れているときは「すべて」に戻し、
右の欄（または履歴の画面）の中だけを動かして行を見せる（ページ全体は動かさない）。

### 6.6 再生バー

上から順に、スライダー（統制の位置に赤い印）、記録の最初と最後の日付、操作ボタン、位置と時刻、速度。
速度は履歴の絞り込みと同じセグメント（`aria-pressed`）で選ぶ。1つ戻る / 1つ進むは `❙◀` / `▶❙` で対にする。

### 6.7 スタイルの決まり

- **同じセレクタを2か所で定義しない**。1か所にまとめる
- 基本の指定は、狭い画面（メディアクエリ）より**前**に置く。後ろに置くとメディアクエリを打ち消す
- 再生位置で高さが変わる欄は、必要な高さをブラウザで全位置測って決める（REQ-022）

### 6.8 狭い画面（REQ-028）

幅 720px 以下では配置を変える。**要素の高さは位置によって変えない**（REQ-022）。

| 箇所 | 狭い画面での形 |
|---|---|
| プロジェクトナビ | 横1行のチップ。停止の件数をチップの中に入れ、選択中は前景色で塗る |
| 画面の切り替え | 横1行のチップ。件数を添える。末尾に「履歴」を置く |
| 履歴 | 右の欄をやめ、`#/p/<案件ID>/history` の画面として本文に出す（広い画面ではチップを出さない） |
| 工程ボード | 1工程1行の縦リスト（記号 / 名前・ゲート / 状態）。横スクロールは使わない。ゲートの層は記号だけを並べる |
| いま起きたこと | 帯は1行（時刻は再生バーに出るので省く）。見出し2行・説明3行分の高さを確保し、入りきらない文は欄の中で繰る |
| 再生バー | 上段にスライダー、中段に高さ 40px 以上のボタン（⚑ 次の停止へを含む）、下段に速度と位置・時刻 |

### 6.9 画面の用語（REQ-027）

画面では次の言い換えを使う。**プロセス定義に由来する名前（Phase 名・ゲート名・G1〜G4・逸脱の種別 ID）は変えない**。

| 定義・内部 | 画面の表示 |
|---|---|
| 案件 | プロジェクト |
| Phase ボード | 工程ボード |
| タスク | AI の作業 |
| ゲート | 品質検査（カード内の「4層品質ゲート（G1→G4）」は定義どおり） |
| トレーサビリティ | 要件⇔テスト対応 |
| 証跡 | 監査記録 |
| 統制記録 | 統制に関わる記録 |
| 逸脱 | 例外処理（エスカレーション → 人の判断待ち、ローカル退避 → ローカル作業へ切替） |
| 出来事の記録 | 履歴 |

### 6.10 公開済みの実物（REQ-029）

- `tools/build_artifact_links.py` が公開 J-SIX の Git オブジェクトと既存イベントから `data/artifact-links.json` を生成する（ADR-0005）。イベント列は変更しない。
- 索引は案件 ID・イベント ID → リンク配列。各リンクに `role`（input/output/reference/source）、完全な commit SHA、任意の path、label を持つ。案件ごとのイベントファイル SHA-256 を保持し、CI で古い索引を検出する。
- Git コミットの差分と変更後の実ファイルをリンクする。Phase ごとに分割したイベントは元の成果物分類で絞る。削除ファイルは存在しない blob へリンクせず、コミットの差分で確認する。
- 入力は版の固定イベントに明記された資料だけ。作業前の仕様・タスク定義は親コミットの「参考」であり、AI が読んだという主張をしない。
- 履歴の行ボタンの外、展開した詳細内だけに表示する。先頭3件を出し、残りは `details` で開閉する。URL 全文は出さず相対ファイル名を折り返す。新しいタブで開く旨を表示し、`noopener noreferrer` を付ける。
- 非公開セッション・版未特定のレポートにはリンクしない。証跡の `payload.commit` は検査対象の版なので保存先 URL に転用しない。確認できない証跡は監査記録画面で説明する。
- リンク先は元イベント時点の固定版、参考はその親の版。出力の内容は当時のものであり、現在の修正版ではない。実物の存在と再構成イベントの実在を混同しない。

## 5. 品質ゲートの設定

- カバレッジと mutation score の閾値は置かない（ADR-0002）。最初のリリースで計測する
