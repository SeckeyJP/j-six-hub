# 要求 Spec — 開発者が J-SIX 全工程を通すローカル Hub PoC

**版**: 0.1 | **日付**: 2026-09-27 | **状態**: 提案中（未実装）

本書は[J-SIXプロセス](https://github.com/SeckeyJP/j-six/blob/main/docs/J-SIX.md)の Phase 0〜6を、単一PCの合成案件で開発者が操作するための要求である。[単一 run の要求](local-execution-requirement-spec.md)を置き換えず、Phase 4 の実行部分に組み込む。現行の[リプレイ要求](requirement-spec.md)と公開 Pages は閲覧専用の説明物として維持する。J-SIX プロセスの正は本体 `docs/J-SIX.md`、機械可読な入力はハッシュ固定した `process/jsix-process.yaml` とする。

## 1. 対象と用語

初回は一人の利用者が、このMacで公開・合成の小さな案件を一巡する。既存 `examples/approval-workflow` を題材候補とし、完成済みの履歴を新たなHub実績として流用しない。基準commitから小さな新規変更を行い、必要な成果物・判断を新たに記録する。企業実PJ、実顧客、複数利用者、複数ベンダー、正式な検収は対象外。

| 用語 | 意味 |
|---|---|
| 開発者ワークベンチ | localhost の案件別操作画面。次の作業、提出物、ゲート不足理由、タスク実行、差分・検査・差戻しを扱う |
| 中央監視 | 同じローカル記録から案件横断の Phase・run・保留・証跡を読む画面。公開リプレイとは別 |
| ローカル模擬判断 | 単一利用者が顧客・レビューア等の役割を**模擬して**記録する判断。本人認証済みの承認・第三者レビューではない |
| 提出 | Gitの対象commit、成果物path・内容hash・要求ID・適用方針版を固定し、Hubの非公開台帳に追記する操作。ファイル名だけの登録は不可 |
| 通過 | 対象版に必要な証拠・実検査と、模擬判断の条件が揃ったローカル工程遷移。正式なJ-SIX工程適合の認定ではない |

公開リプレイ、ローカル模擬操作、実CLI実行の来歴を混ぜない。成果物の正本は対象Git、Hubの判定・操作記録の正本は公開repoと別のリモートなし非公開Git台帳。生ログ・認証cache・秘密値は公開repoにも台帳にも入れない。

## 2. 利用者の一巡

| Phase | 開発者が行うこと | 遷移のための根拠 |
|---|---|---|
| P0 憲法 | 対象repo/基準commit・固定process版を登録し、`CLAUDE.md` と検証環境を確認する | 憲法の対象版と内容hash。J-SIXはP0に人間承認ゲートを定義しないため、Hub独自の「P0承認」を作らない |
| P1 要求 | ユースケース、REQ、PROP、受入条件、非機能条件を提出する | 要求Specと業務フロー/プロトタイプの版、未確定項目の担当・解消Phase、顧客役割の**模擬**合意記録 |
| P2 設計 | Design Spec、ADR、実動プロトタイプ、検証戦略と提出設計書の目次を提出する | 対象版に結び付く設計レビューの模擬記録と未解決事項。逆生成予定物は代替物として明示 |
| P3 タスク | タスクの受入条件・PROP対応、依存、許可/禁止パス、hold-outと必須検査集合を固定する | タスクと変更範囲の模擬承認。固定後の変更は旧許可を失効させる |
| P4 TDD | 対象タスクの hold-out→Red→Green→Refactor とHub管理下のCLI runを進め、候補を検査する | 実際のcommit/差分・テスト結果に結び付くG1→G2→G3→G4。G3省略は `passed` でなく方針に従う省略として記録し最大L3。全タスク完了を確認 |
| P5 品質 | 結合/E2E、要求充足、欠陥、未検証事項とG4証跡を確認する | 実検査結果と品質の模擬判定。代理指標だけでは通さない |
| P6 納品 | 逆生成設計書と他の納品物を対象commitで固定し、レビューする | Phase 2で代替した項目を閉じたこと、納品物一式の模擬レビュー記録 |

## 3. 機能要求

| ID | 要求 |
|---|---|
| REQ-JR-001 | 案件は対象Git repo/基準commit、processのcommit・SHA256、適用方針、合成題材、利用モードを固定して作成する。既存リプレイのイベントを実案件記録へ移さない |
| REQ-JR-002 | P0〜P6の表示名・順序・ゲートID・成果物種別は固定process定義から取得し、定義/ハッシュ不一致・未知IDなら案件の遷移を止める。現行本体とHub lockの差異は移行をレビューしてから採用する |
| REQ-JR-003 | 開発者画面は現在Phase、次の作業、必須提出物、受入条件、提出・レビュー・ゲート結果、差戻し理由、対象commitを一か所で示す。案件横断の中央監視は同じ台帳投影を使用する |
| REQ-JR-004 | 提出物はGit commitとpath、内容hash、型、関連REQ/PROP・対象タスクを記録し、提出時・ゲート判定時に存在とhashを再検査する。空欄や後から書き換えたファイルを過去の提出と同一視しない |
| REQ-JR-005 | Phase遷移は順序、前段の有効状態、必須提出物、ゲートごとの検査・模擬判断、失効を照合する。P0は憲法登録後にP1へ進めるが「承認済み」にしない。必要な情報が欠落・不明なら保留する |
| REQ-JR-006 | 模擬人間判断は役割ラベル、対象commit/成果物hash、判断・理由・時刻・有効期限を明示操作で記録する。画面と台帳で「単一利用者のローカル模擬」と常時区別し、実顧客や独立第三者の承認と表示しない |
| REQ-JR-007 | 差戻し・Phase逆戻り・対象/要求/方針変更では影響する後続判断とrunを失効または再確認待ちにし、過去記録は削除しない。新しい提出・再判定が済むまで次Phaseと候補取込みを止める |
| REQ-JR-008 | P4のタスク実行は[単一run要求](local-execution-requirement-spec.md)の許可、先行Git保存確認、排他、CLI認証・課金ガード、候補差分の独立検査、結果不明時の保留に従う。workerは方針・承認・検査結果を自己発行できない |
| REQ-JR-009 | G1/G2の必須チェックは実行された対象版・設定・結果を記録する。未実装・未実行・skip・unknownを `passed` にしない。G3のLLM所見は参考として発行元と入力版を残し、G4の証跡/要約と区別する。ゲート例外でも元の不合格結果を変更しない |
| REQ-JR-010 | P5の結合/E2E検査とP6の納品物レビューはP4の候補commitと同じ対象系列を参照し、成果物または方針が変わった場合は旧判断を流用しない |
| REQ-JR-011 | localhostの書込APIはHubだけが台帳・候補refを更新し、ブラウザ入力を再検査する。127.0.0.1へのbind、Origin/Host検査、セッション固有トークンとJSON要求、CSRF対策を設け、公開Pagesや外部ネットワークから実行できない。これらは同一OSユーザーに対する強い認証ではない |
| REQ-JR-012 | 画面・API・CLIコマンドは同じドメイン判定を呼び、UIから直接ファイル編集・Git ref更新・CLI spawnをしない。失敗/保留理由と再開に必要な作業を利用者へ示す |
| REQ-JR-013 | UIは案件、Phase、提出物、ゲート、タスク/run、証拠の参照をブラウザでたどれ、キーボードで主要操作ができる。コード編集は外部エディタ/CLIのworktreeで行い、Hubが対象パスと固定版を示す |
| REQ-JR-014 | 中央監視は実run・模擬承認・未検証範囲を区別し、公開リプレイは従来どおり「実際のAIは動作していません」と表示する。ローカル記録・秘密値を静的bundleに含めない |
| REQ-JR-015 | ローカル台帳と対象Gitからサーバー再起動後に案件の工程・不足・保留を再構築する。外部CLIの終了不明をGitの不在だけで未実行と推定しない |
| REQ-JR-016 | 各段階と最終デモの結果を、実行済み・模擬・未実装・未検証に分けて保存・表示する。企業実PJへの一般化や複数主体の承認真正性は主張しない |

## 4. 受入条件

| ID | 対応 | 観測する結果 |
|---|---|---|
| AC-JR-01 | 001〜005 | まっさらなローカル台帳から合成案件を作り、P0〜P6の各提出・判定をブラウザで順に操作できる。前段未通過、必須物欠落、内容hash不一致、未知process版での遷移は0件 |
| AC-JR-02 | 004〜007 | 要求変更、Phase逆戻り、差戻し、期限切れ模擬判断の後、旧承認・旧runでは次Phaseへ進めず、新版の再提出と再判定が必要になる |
| AC-JR-03 | 008〜010 | 一つの新規機能タスクに実差分とG1/G2の結果、G3所見または明示省略、G4証跡、P5結合/E2E、P6納品物を結び付ける。欠落・skip・失敗を偽の合格にしない |
| AC-JR-04 | 011〜014 | 開発者画面から操作、中央監視から同じ状態を読める。公開Pagesのリプレイは不変。外部Origin/Host、無トークン、非JSON、古い版の書込を拒否する |
| AC-JR-05 | 015〜016 | サーバー再起動で同じ工程・提出・保留を復元し、実CLI結果不明はunknownのまま残る。画面に模擬/実行/未証明の境界が見える |

最終ブラウザ受入れでは、新しい基準commitからP0→P6を一巡し、P1差戻しとP4検査失敗の拒否経路も別に確認する。実CLIは[単一run要求](local-execution-requirement-spec.md)の初回上限内でPhase 4に各CLIの小さな実行を1件ずつ観測し、他のPhaseの人間判断は単一利用者の模擬であることを示す。全Phaseを各CLIで繰返すことや、実顧客の承認は要求しない。
